## Categories

| Category | In scope | Finding | Disposition |
|---|---|---|---|
| A01 Broken access control | Yes | `/auth/me` (`src/auth/auth.controller.ts`) reads identity exclusively through `@CurrentUser()` (`src/auth/decorators/current-user.decorator.ts`), which returns whatever `JwtAuthGuard` verified and attached to the request - there is no query parameter, header or body field the handler reads instead. `RegisterDto` (`src/auth/dto/register.dto.ts`) accepts an optional `roles` field for contract conformance, but `AuthService.register` (`src/auth/auth.service.ts`) hard-codes `roles: ["CUSTOMER"]` and never reads `dto.roles` - confirmed by a unit test (`auth.service.spec.ts`, "creates a user with CUSTOMER regardless of a caller-supplied roles field") that supplies `roles: ["ADMIN"]` and asserts it never reaches storage. | None found. Verified by code inspection and the test named above; no action required. |
| A02 Cryptographic failures | Yes | Passwords: argon2id, m=64 MiB, t=3, p=1 (`src/users/password-hasher.ts`), ~110ms measured locally - see the file's own comment for the OWASP basis and why parallelism is pinned to 1. Signing: HS256 is pinned as a literal option on both the signer (`TokenService.createAccessToken`) and the verifier (`JwtAuthGuard`, `algorithms: ["HS256"]`) - the algorithm is never read from the token itself. `JWT_SECRET` has no default (`ConfigService.getOrThrow`); the service fails to start rather than sign with a value nobody chose. Refresh tokens are stored as a SHA-256 hash of a 256-bit random value, never the token itself (`refresh_tokens.token_hash`, no plaintext column exists in the schema). | Refresh tokens use a fast hash (SHA-256), not a slow KDF, which is the opposite choice from passwords. This is intentional and stated in `refresh-token.service.ts`: a refresh token is 256 bits of random data, not a low-entropy human password, so a fast hash already makes a stolen database read not equal a stolen session, and a slow KDF here would only be a self-inflicted DoS surface with no offline-attack benefit. Accepted as the correct tool for this value, not a gap. |
| A03 Injection | Yes | Every statement that touches the credential store or the refresh-token store (`users.repository.ts`, `refresh-token.repository.ts`, `db/schema.ts`'s bootstrap DDL) is parameterised (`$1`, `$2`, ...) via `pg`. No statement is assembled by concatenating a caller-supplied value into SQL text. | None. Every repository file was read end to end for this review; none contains string-built SQL. No action required. |
| A04 Insecure design | Yes | Three design decisions the contract calls out by name, all built rather than merely documented: refresh rotation with reuse detection (`RefreshTokenService.rotate` revokes every live token for a user on a replayed presentation - SEC4-627); the login throttle (5 attempts / 5-minute window per caller IP - SEC4-628); and the uniform login failure (unknown user and wrong password share status, body and argon2id work - SEC4-628). Registration issues no tokens (`AuthService.register` returns `UserResponseDto` only; confirmed by the "issues no tokens on registration" test). | Fixed - all three built, not accepted as risk. **JWT_SECRET rotation** (whether to keep or rotate the development secret published in `.env.example` now that a real issuer signs with it) is SEC4-629's decision and is recorded further down this document once that ticket lands on this branch - see the note at the end of this table. |
| A05 Security misconfiguration | Yes | `JWT_SECRET` and the database credentials have no default and fail startup if missing (`getOrThrow` throughout); only `JWT_ISSUER` (default `auth-service`, matching the contract) and `DB_PORT` (default `5432`, not sensitive) have defaults. The container ran as root (the `node:20-alpine` default) with no CORS policy configured. | Container-as-root: **fixed** - `Dockerfile` now switches to the image's built-in unprivileged `node` user before `CMD` (verified: `docker build` succeeds and a `process.getuid()` check inside the built image returns `1000`, not `0`). CORS: **out of scope** - this service has no browser caller yet; Sprint 9's Angular UI will need an explicit allow-list added when it starts calling this service directly, not the wide-open default. Unhandled faults: **none found** - `PlatformExceptionFilter` only handles `HttpException`; anything else falls through to Nest's default handler, which logs the full error server-side and returns a generic message to the client regardless of environment, so no stack trace reaches a response body. |
| A06 Vulnerable and outdated components | Yes | `npm audit` (run against the committed `package-lock.json`) reports 5 high-severity advisories, all the same root cause: `multer` (pulled in transitively by `@nestjs/platform-express`, itself pulled in by `@nestjs/core`/`@nestjs/swagger`/`@nestjs/testing`) has known DoS advisories in multipart-form parsing. | Accepted, with residual risk stated: this service has no route that accepts `multipart/form-data` - all four contract endpoints take `application/json` - so `multer`'s parsing path is never reached by an external request. The fix (`npm audit fix --force`) is a breaking major-version bump of the whole `@nestjs/*` tree, out of proportion to a code path this service never exercises. Revisit when Nest 12 is the team's stable target across services. `package-lock.json` is committed and `npm ci` pins exact versions. |
| A07 Identification and authentication failures | Yes | Uniform failure and the throttle (see A04) are built and unit-tested. Access token lifetime is 15 minutes, refresh token lifetime is 7 days (`TokenService.ACCESS_TOKEN_TTL_SECONDS`, `RefreshTokenService.REFRESH_TOKEN_TTL_SECONDS`), matching the contract. Expiry is checked on every protected request - `JwtAuthGuard` calls `jsonwebtoken.verify` fresh on each call; there is no cache of "already valid," so a token that expires mid-session is refused on its very next use. Minimum password length: `RegisterDto.password` enforces `@MinLength(12)`, matching the contract's `minLength: 12`. | None found against the checks above. No action required. |
| A09 Security logging and monitoring failures | Yes | Before this review pass, no security-relevant event was logged anywhere in the service - a login failure, a login success, a throttle trip, a successful refresh and a detected refresh-token replay all happened silently. | Fixed (see the commit "Log the events A09 asks a service to be able to answer for"): `AuthService` and `RefreshTokenService` now log one structured event each for `user_registered`, `registration_conflict`, `registration_unknown_account`, `login_succeeded`, `login_failed`, `login_throttled`, `refresh_succeeded` and `refresh_reuse_detected`. Every call names only a username, user id, account id or caller IP - never a password, a hash or a token. All logging goes through Nest's `Logger`, which `main.ts` backs with `RedactingLogger` (SEC4-624): any field named `password`, `passwordHash`, `accessToken`, `refreshToken`, `authorization` or `token`, at any depth, in anything logged anywhere in this process, is replaced with `[REDACTED]` before it reaches the console - including inside a serialised `Error` object, which is the indirect route the ticket names. |

### Categories deliberately absent

A08 (software and data integrity failures) and A10 (server-side request forgery) are not rows in this table, matching the template's own guidance: A08 is covered by A06's dependency-pinning discussion above, and A10 needs the service to make outbound requests on a caller's behalf, which this one does not (it calls no external HTTP service).
